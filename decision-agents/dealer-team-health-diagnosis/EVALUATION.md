# 评估记录

## 当前结论

当前版本只完成了技术冒烟检查和信息架构验证，尚未完成真实业务数据回测或运营用户测试。因此不能声称健康度分数、风险提示或 AI 诊断具备业务准确率。

## 已完成检查

运行：

```bash
node tests/smoke-test.js
```

检查内容：

- HTML 中的 JavaScript 可以解析；
- 默认进入全体团队 Overview；
- Overview 的重点名单数量与规则筛选结果一致；
- 健康度、归因和风险三个页面可以生成；
- 未命中某风险类型时显示空状态；
- 页面不再展示未经校准的固定置信度。

当前 Mock Data 下，规则筛出 6 个重点团队。该数字只用于验证 Demo 内部一致性，不代表真实业务分布。

## 基线

后续评估至少比较两种流程：

1. **传统看板基线**：用户自行查看指标并选择团队；
2. **诊断流程**：系统先展示整体画像，再筛选重点团队并解释原因。

当前尚未采集两种流程的任务时间、正确率或用户理解数据。

## 下一轮测试计划

| 评估对象 | 指标 | 方法 |
|---|---|---|
| 排序有效性 | Top 3 重点团队人工确认率 | 用历史月份数据与运营复盘结论对照 |
| 风险准确性 | 各规则精确率、召回率、误报率 | 建立带结果标签的回测样本 |
| 可解释性 | 用户能否说出主要失分来源 | 任务后访谈与理解测试 |
| 效率 | 完成首个团队诊断的时间 | 与传统看板进行同任务对比 |
| 稳定性 | 相近输入是否产生稳定分层 | 边界值和扰动测试 |
| 公平与边界 | 是否系统性偏向大团队或高销售团队 | 按规模、区域和成熟度分组检查 |

## 需要重点验证的失败案例

- 目标达成较高但高度依赖少数核心成员；
- 总活跃率稳定但新人持续断档；
- 小团队因样本量小而分数剧烈波动；
- 数据缺失被错误解释为经营恶化；
- 标签同时命中太多，导致优先级失去区分度；
- 月末临期规则在不同业务周期下产生误报。

## 发布门槛

进入真实 Pilot 前，应至少完成数据字典、缺失值规则、时间窗口、阈值回测、误报复核流程和个人信息保护评审。
